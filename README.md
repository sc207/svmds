# SVMDS — Shri Vihat Meldi Mata Mandir

Temple management platform for **Shri Vihat Meldi Mata Mandir, Sanand, Gujarat** —
devotees, donations (cash **and** in-kind, with 80G receipts + Dhanyavaad
certificates), poojas & sevas, festivals/events, volunteer teams (Management),
Samaj/Committee governance, a Bappa/Bhuvaji padhramani register, a unified
calendar, role-scoped dashboards, an Accounts & Access console with a live audit
trail, a global ⌘K command search, and PDF / Excel / CSV export everywhere.

Trilingual — **English / हिन्दी / ગુજરાતી**. Data entry stays in English; all
display text, dates and fixed vocabulary localise.

The repo has two parts:

| | Stack | State |
| --- | --- | --- |
| **Frontend** (`index.html`, `css/`, `js/`, `assets/`) | static, no-build, vanilla-JS single-page app | complete & in use |
| **Backend** (`server/`) | Node 20 · Express · SQLite (dev) / Turso libsql (prod) · passwordless TOTP auth · revocable sessions | Phase 0 — scaffold + schema; see [`BACKEND_PLAN.md`](BACKEND_PLAN.md) |

---

## Run the frontend

Open `index.html` directly, **or** serve the folder statically:

```bash
python -m http.server 8000        # then http://localhost:8000
```

Any static server works (`npx serve`, VS Code Live Server, …). All asset /
script / stylesheet paths are relative, so it runs from a project sub-path
unchanged. Today all data is an **in-memory seed** in `js/*.js` — every reload
resets it; only the temple-identity form, language and the working-date clock
touch `localStorage`.

## Run the backend (development)

```bash
npm install
cp .env.example .env               # ADMIN_EMAIL + a JWT_SECRET are enough for dev
npm run migrate -- --seed          # create data/svmds.db, apply migrations, seed catalogs
npm start                          # http://localhost:3000  (health: /health)
```

With `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN` **unset**, the backend uses a
local `data/svmds.db` (better-sqlite3). Set both to target a Turso database.
`SMTP_*` unset ⇒ login OTPs print to the server log instead of being emailed.

### npm scripts

| Script | Does |
| --- | --- |
| `npm start` | run the server (migrations run on boot) |
| `npm run migrate` | apply pending `server/db/migrations/NNN_*.sql` |
| `npm run seed` | migrate + idempotent reference data (catalogs, committees, counters, settings) |
| `npm run demo` | seed + demo data (only into empty tables) |

## Deployment

Blueprint-driven on **Render** with a **Turso** (libsql) database — both named
`svmds`. `render.yaml` describes the web service; `JWT_SECRET` is generated by
Render, the rest of the secrets (`ADMIN_EMAIL`, `TURSO_*`, `SMTP_*`,
`ALLOWED_ORIGINS`) are set in the dashboard. Full steps and the phased rollout
are in [`BACKEND_PLAN.md`](BACKEND_PLAN.md) §1 and §11.

## Project structure

```
index.html            single page — shell markup + script/style links
render.yaml            Render Blueprint (service: svmds)
.env.example           backend env template
BACKEND_PLAN.md        full backend implementation plan (schema, auth, rollout)

css/styles.css         the hand-authored design system (maroon / saffron / gold)
assets/                icon.png (emblem) + temple.png — used across UI, badges,
                       invitations, receipts, certificates and PDFs
js/
  i18n.js              trilingual layer (loads first)
  people.js            ACCOUNTS registry — who has a login and what they can open
  export.js            CSV / Excel / certificate-grade PDF export service
  app.js               core SPA shell, routing + access guard, core records
  search.js            global ⌘K command search across every store
  management.* pooja.* donations.* committee.* events.*   module = store / -ui / -forms
  visits.js            Bappa / Bhuvaji padhramani register
  calendar.js          unified cross-module month calendar (+ mobile agenda view)
  dashboard.js         role-aware dashboard cockpit + "how it works" guide
  access.js            Accounts & Access / Reports / Settings pages

server/
  index.js             app entry — middleware, routes, boot sequence
  config.js            the only reader of process.env
  db/
    connection.js      better-sqlite3 (dev) / @libsql/client (Turso) abstraction
    migrate.js         numbered forward-only migration runner
    migrations/        001_init.sql … (36 tables + calendar views, CHECK + FK throughout)
    seed/              reference-data.js (idempotent) · demo-data.js
  middleware/           error handling (auth / authz land in Phase 2)
```

Frontend script **load order matters** and is fixed in `index.html`
(`i18n → people → export → app → management.* → pooja.* → donations.* →
committee.* → events.* → visits → calendar → dashboard → access → search`).

There is no lint / test step — frontend verification is manual in the browser;
backend verification is `npm run migrate` + `/health`.

## Demo access contexts (frontend, pre-auth)

Until the backend auth lands, use the **role selector** in the top bar (or
**Sign in as** on Accounts & Access) to preview the app as:

| Context | Sees |
| --- | --- |
| Super Admin | the whole platform |
| Management Lead | only their volunteer team(s) |
| Pooja Coordinator | only their assigned poojas |
| Committee Leader | only their Samaj committee(s) |
| Temple Accountant | donations, expenses, reports |

Scoped contexts get a mini-dashboard limited to their own data and cannot open
other modules — the client router enforces it. The backend (Phase 2+) moves this
enforcement server-side with real passwordless login and revocable sessions.
